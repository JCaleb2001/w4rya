Sobre w4ryacapítulo 01

w4rya es un analizador de flujos de red diseñado para usarse durante competencias Attack/Defense (A/D) de CTF. Ingiere los pcaps que captura tu vulnbox, los descompone en flows, los enriquece con tags (incluyendo alerts de Suricata si está activo), y los expone en una UI web pensada para que un equipo opere en simultáneo: buscar el ataque que acaba de robar un flag, escribir una regla Suricata para bloquearlo, y rebotar el mismo exploit a los otros teams.

Stack

ComponenteTecnologíaRol
IngestorGo (gopacket)Lee pcaps, reconstruye flows, escribe a Timescale
APIPython FlaskQuery + auth + config + rules + replay
FrontendReact + Vite + TailwindOperación en vivo
DBTimescaleDB / PostgresPersistencia + extensión C custom
SuricataContainer opcionalIDS/IPS, eve.json → enricher
Restricción permanente

Este tool nunca llama a un servicio de IA/LLM en tiempo de ejecución. Las competencias A/D donde está pensado correr prohíben uso de IA durante el juego. Toda la clasificación es determinista: regex, signatures de Suricata, heurísticas estadísticas. PRs que agreguen llamadas a OpenAI/Anthropic/cualquier API de LLM serán rechazados.

Basado en

Hard fork de Tulip (github.com/OpenAttackDefenseTools/tulip) que a su vez es un fork de flower (github.com/secgroup/flower). Toda la arquitectura del ingestor y la base del frontend vienen de Tulip; w4rya agrega auth con roles, exploit testing, war-room mode, audit log, polish de UI dark hacking, y hardening para uso en vivo.

Instalación y primer arranquecapítulo 02

Requisitos

  • Docker 24+ con docker compose v2
  • 4 GB RAM mínimo recomendado (8 GB para CTFs con mucho tráfico)
  • Tu usuario en el grupo docker para no usar sudo

Clonar y configurar

git clone https://github.com/JCaleb2001/w4rya.git
cd w4rya

cp .env.example .env
# editar .env: poner un W4RYA_SECRET_KEY (ver más abajo)

El secret key es obligatorio. Genéralo con:

openssl rand -hex 32

Copialo dentro de .env en la línea W4RYA_SECRET_KEY=.... Sin este valor el api se niega a arrancar.

Levantar el stack

docker compose up -d --build

Esto levanta 6 containers: timescale, api, frontend, assembler, enricher, flagids. La primera vez tarda ~3-5 min compilando la extensión Postgres y el ingestor Go.

Verificar que arrancó

docker compose ps                          # los 6 containers en Up
curl http://localhost:3001/api/healthz     # → {"db":"up","ok":true}

Crear el usuario admin inicial

docker compose run --rm api python /app/auth/add_user.py <username>

Prompts interactivos para password (no se ve mientras tipeas). El primer usuario que crees queda con role admin por back-compat (los entries sin role: default a admin). Usuarios futuros via el mismo script defaultean a viewer; usá --role admin|operator|viewer para especificar.

Footgun

NO uses sudo con ese comando. El file auth/users.yaml queda root-owned en el host. Si ya lo hiciste: sudo chown -R $USER:$USER auth/.

Abrir la UI

Navegá a http://localhost:3001. Login con el usuario que acabás de crear. Te redirige al dashboard.

Variante con Suricata

Para activar IDS/IPS, levantá con docker compose -f docker-compose-suricata.yml up -d --build. Necesitas también SURICATA_DIR_HOST en .env apuntando a un directorio host donde Suricata escribe logs.

Auth y rolescapítulo 03

Tres tiers de permisos, en orden ascendente:

RoleLo que puede hacer
viewerBrowse flows, ver dashboard, war-room. Postear notas. Login/logout.
operatorTodo lo anterior +  editar Suricata rules, reload Suricata, test-exploit replay, quick-block IP, star flow.
adminTodo +  /config (services/teams/game vars) +  /audit.

La UI esconde los botones que no podés usar; el backend de todos modos los protege con 403.

Crear usuarios

docker compose run --rm api python /app/auth/add_user.py alice --role operator
docker compose run --rm api python /app/auth/add_user.py bob   --role viewer
docker compose restart api      # opcional, mtime cache también lo agarra

Rotar password

Mismo comando con el mismo username: sobrescribe el hash y el role.

Borrar un usuario

Editar auth/users.yaml a mano, eliminar el bloque correspondiente, docker compose restart api.

Rotar el secret key (invalida todas las sesiones)

NEW=$(openssl rand -hex 32)
sed -i "s|^W4RYA_SECRET_KEY=.*|W4RYA_SECRET_KEY=\"$NEW\"|" .env
docker compose restart api

Rate limiting

El endpoint /login tiene un token bucket en memoria: 5 intentos fallidos en 5 minutos por cada par (ip, username) → 429 con retry_after_sec. Cada gunicorn worker tiene su propio contador, así que en práctica con 3 workers el techo efectivo es ~15 intentos. Suficiente para frenar scripting básico.

Sessión cookie

Nombre w4rya_session, httpOnly, SameSite=Lax, 7 días de vida. Para HTTPS poné W4RYA_COOKIE_SECURE=1 en .env antes de servir por TLS.

Configuración inicialcapítulo 04

Antes de empezar a usar w4rya en un CTF real, necesitás configurar 3 cosas en /config (solo admin):

Tab "game"

Variables del juego que se aplican al ingestor y a la UI:

VarQué es
flag_regexPatrón regex que matchea el formato de flag del CTF. Ej: [A-Z0-9]{31}=. Validado al escribir (rechaza regex inválido y patrones ReDoS).
tick_startTimestamp ISO8601 UTC del inicio del primer tick. Ej: 2024-11-30T13:00:00Z.
tick_lengthDuración de un tick en ms. Típico 180000 (3 min) o 240000 (4 min).
flag_lifetimeCuántos ticks vive un flag antes de expirar. Default 5.
vm_ipIP de tu vulnbox dentro de la red del juego.
team_idNúmero/ID de tu equipo.
visualizer_urlOpcional: URL del visualizer del CTF (Faust style).
bpfOpcional: BPF filter para limitar captura.
Restart required

flag_regex y bpf también los lee el container assembler al boot. Si los cambiás en vivo, la UI los aplica al instante pero el ingestor sigue con el valor viejo hasta que reinicies con docker compose restart assembler.

Tab "services"

Lista de servicios de TU equipo (los que el ingestor ve cuando rotura el tráfico que cae en tu vulnbox). Cada entry: name, ip, port, notes. Estos se usan para:

  • Etiquetar flows con el service-tag correspondiente
  • Mostrar chips de filtrado en la sidebar del FlowList
  • Stats per-service (flows, attacks, flags-out en los últimos 5 ticks)

Ejemplo: si tu vulnbox es 10.10.3.1 y el servicio "BIOMarkt" corre en :18080, agregás: name=BIOMarkt ip=10.10.3.1 port=18080.

Tab "teams"

Lista de equipos enemigos. Cada entry: name, ip, notes. Esta tabla solo se usa por el exploit replay: cuando dispares "test exploit" desde un flow, w4rya enumera estos team-ips y rebota el payload contra cada uno en su puerto original.

Sin teams configurados, el modal de exploit testing va a estar vacío.

Vista principal: FlowList y filtroscapítulo 05

El dashboard tiene tres áreas:

┌─ HEADER ──────────────────────────────────────────────────────┐ │ [logo] w4rya [search] [date pickers] [Last 5] [Graph] │ │ [Attacks] [Warroom] [Config] [Rules] [Audit] [user] │ ├──────────────────┬────────────────────────────────────────────┤ │ FlowList sidebar │ Flow detail (Outlet) │ │ ─────────────────│ ───────────────────────────── │ │ [Open filters] │ Home / Flow / Diff / Corrie / Config … │ │ chips, search │ │ │ │ │ │ ▶ flow #1 ★ │ │ │ ▶ flow #2 │ │ │ ▶ flow #3 │ │ └──────────────────┴────────────────────────────────────────────┘

Buscar y filtrar

El sidebar tiene un panel de filtros (botón "Open filters") con dos secciones:

  • Services: chips multi-select de los services configurados. Click toggle. Cada chip muestra mini-stats (flujos/⚔/🚩 últimos 5 ticks). El borde del chip refleja presión: violeta normal, amarillo bajo alerta Suricata, rojo si perdiste flag.
  • Tags intersection: chips de tags (incluyendo flag-in, flag-out, starred, etc). Tres estados: deshabilitado, incluido, excluido (negro tachado). Modo AND/OR para múltiples tags.

En el header:

  • Search bar: regex case-insensitive sobre el contenido de los flows (debounced 300ms)
  • Date pickers: tick start / end manual
  • "Last 5 ticks": shortcut

Inspeccionar un flowcapítulo 06

Click en cualquier flow del sidebar abre /flow/<id> en el panel derecho.

Estructura

  1. Toolbar secundario (sticky top): nav parent/child, selector de decoder (raw / http-decoded / etc), "Diff" para representaciones diferentes, "Copy as pwntools", "Copy as requests", "▶ test exploit".
  2. Suricata card (si el flow disparó alguna regla): rule msg, rule id, action (alert / drop).
  3. Meta card: tags, tick, service, flags-in/out, src→dst, duración. Botón "block" al lado del src_ip que crea regla Suricata DROP automáticamente.
  4. Notes panel: scratchpad del equipo (ver §11).
  5. Flow items: cada request/response del flow renderizado según el modo elegido:
ModoCuándo
PlainTexto crudo del wire. Default.
HexHexdump (formato twos). Para protocolos binarios.
WebHTTP only: renderiza el body en un <iframe> sandboxed. Útil para ver una respuesta HTML como la vería un browser.
PythonRequestGenera el snippet equivalente con la lib requests. Copy → pegar en tu farm.

Highlights en el body

El texto del flow tiene dos highlights automáticos:

  • El query del search bar (si está activo) en violeta translúcido
  • Cualquier match del flag_regex en rojo translúcido (más vistoso, indica leak)

Export

  • Download: bytes crudos del flow item, archivo binario
  • Download body (solo Web): body decodificado
  • Open in CC: abre el contenido en CyberChef (gchq.github.io). Nota: este botón envía data a github.io — no clickear con flags reales si te preocupa privacidad.
  • Copy as pwntools / Copy as requests: snippets listos para tu farm

Diff entre representaciones

Si un flow tiene varios decoders (ej: raw + http-decoded), podés diff entre ellos con el botón ⚡. Útil para detectar cambios en encoding (ej: gzip + raw).

Test de exploits + script para farmcapítulo 07

El feature más A/D-específico. Workflow esperado:

  1. Un equipo enemigo te exploitea — ves un flow en el FlowList con tag flag-out o una alerta Suricata.
  2. Abrís el flow, identificás el payload del request enemigo.
  3. Click "▶ test exploit". Se abre el modal.
  4. El modal toma los items con direction=c (cliente → servidor) y los concatena como payload. Te muestra preview (bytes, puerto, src/dst originales).
  5. Seleccionás contra qué teams disparar (default: todos los /config/teams). Setteás timeout (default 3s).
  6. "▶ replay against N target(s)" → fan-out paralelo (max 16 workers, deadline overall 45s < gunicorn -t 60s).
  7. La tabla de resultados se ordena: hits primero, después OK, después errores. Cada fila muestra: team, target IP, status (✓ FLAG / ○ no flag / ! ERR), latencia, response size, conteo de flags capturadas, excerpt.
  8. Click una fila → expande con el body completo y los flag values encontrados.

Descargar el exploit para el farm

El botón "↓ download exploit script" baja un .py standalone (sin dependencias externas) con:

  • El payload embebido como hex literal
  • La lista de teams configurados, baked in
  • El flag_regex
  • Un main() que loopea por team, abre socket, sendall, captura, regex-matchea, imprime
  • Un comentario # TODO: pipe captured into your farm/submitter donde plug-ueás tu lógica de submission
Límite del replay actual

El payload se envía tal cual fue capturado. Funciona para exploits stateless. Si el exploit dependía de un flagid específico por-team, vas a necesitar editar el script generado para inyectar el flagid correcto (esto está en roadmap como "tokenized flagid replay").

Caps

  • MAX_TARGETS: 64 por replay
  • Per-target timeout: max 15s
  • Overall deadline: 45s
  • Response truncado a 256 KB
  • Excerpt mostrado: primeros 1 KB

Suricata rules + quick-blockcapítulo 08

/rules permite gestionar el file suricata-rules/suricata.rules sin tocarlo a mano. Solo operator/admin.

Vista

  1. Header: path del file, count de rules, botón "+ new rule"
  2. Suricata control bar: status del socket (reachable / offline), botón "▶ reload now", toggle "auto-reload on save"
  3. Templates dropdown: 5 reglas pre-cargadas (SQLi UNION SELECT, path traversal, /etc/passwd, shell metachars, drop sqlmap UA)
  4. Tabla de rules: enable-toggle, sid, action (color-coded: drop=rojo, alert=violeta), msg, edit/delete

Crear regla

Click "+ new rule" o pick un template → se abre form con textarea. Pegás Suricata raw rule:

alert http any any -> any any (msg:"path traversal"; flow:to_server;
  content:"../"; http_uri; metadata: tag path_traversal; rev:1;)

Si no incluís sid:N;, w4rya te auto-asigna uno desde 1.000.000. Si los parens están desbalanceados (rule pegada mal), el save rechaza con error (no quiere splicear sid en medio de un content).

Enable / Disable / Delete

Toggle en cada fila. "Disable" prepende # a la línea (convención Suricata). "Delete" la elimina por completo.

Quick-block desde un flow

En /flow/<id>, al lado del src_ip, hay un botón "block". Confirm → genera automáticamente:

drop ip <src_ip> any -> any any (msg:"w4rya:block:<src_ip>@<ts>";
  metadata: tag blocked; sid:<auto>; rev:1;)

Visual feedback: ✓ blocked verde por 3s, después vuelve a "block".

Auto-reload

Activando el toggle auto-reload on save, cualquier CRUD de rules dispara también reload-rules sobre el socket unix de Suricata (/var/run/suricata/suricata-command.socket). El socket lo expone Suricata con el flag --set unix-command.enabled=yes (ya wired en el compose).

Si Suricata no está corriendo, el save igual funciona y la respuesta incluye reload.kind=socket_missing. La UI muestra el error sin romper el save.

Reload manual

Si tenés auto-reload OFF y guardás cambios, podés reloadear cuando quieras con el botón "▶ reload now" del control bar.

Notas y alertascapítulo 11

Notes por flow

Panel debajo del Meta card en /flow/<id>. Cualquier usuario autenticado puede postear, hasta 10000 chars. Útil para coordinar: "este SQLi funciona", "ya tengo exploit para esto", "@alice mirá", etc.

El author del note se setea automáticamente (session user). Solo el author puede borrar su propia note (admin no puede borrar notas ajenas).

Toasts globales

Sistema de notificaciones bottom-right de la pantalla. 4 severidades con color: info (violeta), success (verde), warning (ámbar), danger (rojo). Auto-dismiss después de N segundos o click ✕.

Algunas toasts incluyen un link "open →" que navega directo al flow relacionado.

Flag-leak alarm automática

FlagLeakWatcher es un componente background que polea /query?tags_include=flag-out cada 15s. La primera vez pobla un "seen set" sin disparar nada (no quiere alertar de leaks históricos). De ahí en más, cualquier nuevo flow con flag-out dispara toast danger con link.

El polling se pausa cuando la tab está hidden.

Backupscapítulo 13

Script scripts/backup.sh snapshot atómico de toda la state operacional:

  • auth/users.yaml (usuarios + roles + hashes)
  • suricata-rules/*.rules (todas tus reglas)
  • .env (con W4RYA_SECRET_KEY — sensible)
  • pg_dump de las 3 tablas DB: app_config, flow_notes, audit_log

Output: ./backups/w4rya_<UTCISO>.tgz. Directorio backups/ gitignored (contiene secrets).

Uso

./scripts/backup.sh
# o customizando dir:
BACKUP_DIR=/srv/w4rya-bk ./scripts/backup.sh

Cron sample durante CTF

# cada 5 min
*/5 * * * * cd /home/user/w4rya && ./scripts/backup.sh >> /tmp/w4rya-bk.log 2>&1

Restore

tar xzvf w4rya_20260524T200000Z.tgz -C /tmp/restore
# revisar los .sql, después:
docker compose exec -T timescale psql -U w4rya -d w4rya < /tmp/restore/app_config.sql
docker compose exec -T timescale psql -U w4rya -d w4rya < /tmp/restore/audit_log.sql
docker compose exec -T timescale psql -U w4rya -d w4rya < /tmp/restore/flow_notes.sql
cp /tmp/restore/users.yaml auth/users.yaml
cp /tmp/restore/*.rules    suricata-rules/
docker compose restart api
Cuidado dónde van los tgz

El tarball contiene .env + bcrypt hashes. Si los compartís off-host, encriptalos primero (gpg --symmetric) o usá storage con ACL.

Tests automatizadoscapítulo 14

Suite pytest dentro del container api. 29 tests, ~0.3 segundos.

Cubre las pure-function paths que más fácil rompen en silencio:

  • rate_limit: bucket, expiry, clear
  • app_config.coerce_scalar: int, bool variants, regex valid/invalid/ReDoS, string passthrough
  • rules.parse_one: rule válido, disabled, blank, comentario, garbage-preserves-raw
  • rules._inject_sid: adds-when-missing, no-op-when-present, no-dup-rev, refuses-unbalanced, no-parens
  • rules round-trip: add+list+toggle+delete sobre tmp file, block_ip happy + quote-injection guard
  • attack: hex block format/wrap/empty, build_payload empty + client-only filter

Correrlos

docker compose exec api python -m pytest /app/tests/ -v

Salida esperada: 29 passed in 0.3s.

Troubleshootingcapítulo 15

El api no arranca

  • "W4RYA_SECRET_KEY env var is required" → poné un valor en .env con openssl rand -hex 32
  • "connection to server at … port 5432 failed" → timescale tarda 30-60s en bootear la primera vez; los reintentos del api lo recuperan. Si persiste, mirar docker compose logs timescale

Build de Docker falla con "Temporary failure in name resolution"

BuildKit no resuelve DNS en algunos hosts. Workaround:

docker build --network=host -t w4rya-api:latest \
  -f services/api/Dockerfile-api services/api/

El healthcheck dice "unhealthy"

docker inspect --format='{{.State.Health.Status}}' w4rya-api-1
docker compose logs api | tail -50

Si el endpoint /healthz devuelve 503, suele ser conn pool a timescale roto. Restartear: docker compose restart api.

Me bloqueé en /login

5 fails → 5 min lockout por (ip, username). Esperar, o restartear api para limpiar buckets en memoria: docker compose restart api.

Files root-owned después de sudo

sudo chown -R $USER:$USER auth/ suricata-rules/ backups/

Suricata no recibe rules nuevos

Verificá: (1) suricata está corriendo (docker compose -f docker-compose-suricata.yml ps), (2) la file suricata-rules/suricata.rules contiene tu cambio, (3) el socket existe (ls suricata-run/), (4) reload manual con el botón "▶ reload now". Si nada, restart suricata.

El frontend muestra "no events / no services configured"

Setup primer vez: tenés que configurar services en /config → services. Los pcaps de ejemplo (en services/test_pcap) usan IPs ficticias; mappealas a names en la UI.

Atacantes ven mi w4rya

NO lo expongas a internet. Es para LAN/VPN team-internal. Si DEBE ser remoto: ponelo detrás de un reverse proxy con TLS + setear W4RYA_COOKIE_SECURE=1 en .env. Sin TLS la cookie viaja en claro.
